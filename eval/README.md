# ClaimGraph evaluation harness

Frozen topic corpora → claims → candidate pairs with all signals → baseline / ablation / full-system predictions →
blinded annotation → metrics, tables and studies. Entry point: `scripts/cg_eval.py <command>` (`--help` lists them).

## What is in this repository, and what is not

The numbers of the accompanying manuscript (in preparation, not part of this repository) are recorded in
`eval/results/c4_layers/` (development study) and `eval/results/f1_validation/` (pre-registered validation on three
fresh topics). The inputs behind them that can be shared are included:

| Path | What |
|---|---|
| `topics.json` | topics, dev/test/fresh split, seed papers |
| `FREEZE.json` | when rules, prompts and metrics were fixed, with file hashes and every later change |
| `verify_freeze.py` | read-only check of those hashes (see "Verifying the freeze") |
| `annotation/c4/`, `annotation/f1/` | four-state reference labels (`reference.json`), annotator agreement, sampling keys, raw annotator calls (`model_calls.jsonl`); `f1/PREREGISTRATION.md` |
| `annotation/eval2/` | labels of the earlier five-way protocol (the V1 held-out set), with sampling key and raw annotator calls |
| `ANNOTATION_GUIDE.md` | instructions of the original two-question protocol for human annotators (`sheet`) |
| `frames/c4_frames.json` | per-claim conditional-prediction frames used by experiment E3 |
| `results/c4_layers/`, `results/f1_validation/` | the studies reported in the manuscript |
| `results/v2_dev/`, `results/v2_fourstate/`, `results/eval2_main/` | earlier development studies and the V1 result that `FREEZE.json` refers to; not used for the manuscript's numbers |
| `v2_params.json` | calibrated parameters of the V2 comparability model, which was not adopted |

Not included, because they hold downloaded paper text or are regenerated by the commands below:
`backend/data/eval/corpora/` (frozen full-text snapshots), `eval/runs/` (claims and candidate pairs per topic),
`eval/llm_cache.jsonl` (every LLM response), the annotation sheets, per-item CSVs and plots.

**What this means for reproducibility.** The commands below rebuild the corpora from the seed papers and re-run every
stage, but the live literature and the hosted LLM have moved on, so a rebuilt run is not expected to give the same
claims or pairs. Pair and item ids are hashes of the claims, so the shipped reference labels join only with pairs that
regenerate identically. The studies that read labels (`fourstate-study`, `layer-study`, `fresh-validate`) therefore
cannot be expected to reproduce the published numbers from this repository alone; the shipped result files are the
record. The repository does let you inspect the labels and the raw annotator calls behind them, run the same code on a
new corpus, and check the hashes in `FREEZE.json` against the files they name.

## Commands

```bash
PY=backend/.venv/bin/python          # run from the repository root

$PY scripts/cg_eval.py build-corpus --split all          # 1. download papers, freeze snapshots
$PY scripts/cg_eval.py prepare --split test --run main   # 2. claims + candidate pairs + similarity + NLI
$PY scripts/cg_eval.py llm --split test --run main       # 3. LLM signals (pair analysis + direct baselines), cached
$PY scripts/cg_eval.py describe --split test             # list the papers in the frozen corpora (--topic a,b limits it)
$PY scripts/cg_eval.py report --topic adam_vs_sgd --run main    # terminal view: claims, contexts, pairs, decisions
$PY scripts/cg_eval.py examples --split test --run main -k 3    # qualitative examples per category (--batch eval2 adds gold labels,
                                                                #   --confirmed keeps those the gold relation bears out)
```

`describe` and `examples` take `--split dev|test|all`; neither calls an LLM. Run `scripts/cg_eval.py <command> --help`
for the options of any command.

## Where the code is

The evaluation code is one package, `backend/app/evaluation/`; the data it reads and writes is under `eval/`.

| Purpose | Code (`backend/app/evaluation/`) | Data (`eval/`) |
|---|---|---|
| Harness: corpora, claims, pairs, systems, metrics | `corpus`, `experiment`, `llm_baseline`, `scoring`, `metrics`, `plots`, `report`, `cli` | `topics.json`, `results/` |
| Annotation protocols | `annotation` (two questions, human sheets; with `annotate_template.html`), `model_annotation` (five relations; with `adjudicate_template.html`), `conflict_annotation` (four states) | `annotation/` |
| Checks on the system's output | `explanation_audit`, `rejections` | `results/` |
| Studies | `comparability_study`, `fourstate_study`, `frame_extraction`, `layer_study`, `fresh_validation` | `frames/`, `results/`, `annotation/f1/PREREGISTRATION.md` |

Four-state annotation and the studies reported in the manuscript:

```bash
$PY scripts/cg_eval.py fourstate-annotate [--execute]   # blind four-state labels from three annotator models (prints the cost first)
$PY scripts/cg_eval.py frames-extract [--execute]       # E3: one conditional-prediction frame per claim (cached)
$PY scripts/cg_eval.py layer-study                      # E1-E3 on batch c4 (offline)
$PY scripts/cg_eval.py fresh-sample                     # pre-registered sample for the fresh topics (batch f1)
$PY scripts/cg_eval.py fresh-validate                   # pre-registered E1 validation; run once, never tune on it
```

Earlier five-way protocol (batch `eval2`, V1) and the V2 development studies:

```bash
$PY scripts/cg_eval.py sheet --split test --run main --batch test1 --annotators a1,a2,a3   # two-question protocol: blind sheets for human annotators (ANNOTATION_GUIDE.md); `score --batch test1` reads them back
$PY scripts/cg_eval.py explain --split test --run main                      # grounded explanation for every face-value conflict
$PY scripts/cg_eval.py annotate-sample --split test --run main --batch eval2
$PY scripts/cg_eval.py annotate-run --batch eval2 --dry-run                 # call count + cost estimate
$PY scripts/cg_eval.py annotate-gold --batch eval2                          # consensus, agreement, adjudication worklist, gold.json
$PY scripts/cg_eval.py score --batch eval2 --run main                       # all systems, same pairs, same labels
$PY scripts/cg_eval.py rejections --split test --run main --batch eval2     # why apparent contradictions were rejected
$PY scripts/cg_eval.py explain-audit --split test --run main --name eval2_main
$PY scripts/cg_eval.py v2-study / v2-freeze / fourstate-study               # V2 comparability model on eval2 (development data)
```

## Topics and the dev/test split

`split: dev` topics were used while writing rules and prompts. `split: test` topics are held out: nothing was tuned on
them, and their system outputs were not inspected before the system was frozen. `split: fresh` topics were added later
for the pre-registered validation. Each corpus is a set of seed arXiv papers known to take different positions on the
question, topped up with automatically discovered papers that pass a relevance floor.

## Systems

All systems label the same candidate pairs (cross-paper claim pairs above the embedding-similarity threshold) with a
relation (SUPPORTS, EXTENDS, QUALIFIES, CONTRADICTS, UNRELATED) or abstain on a face-value conflict they will not assert.

| Name | What it is |
|---|---|
| `similarity` | every candidate pair is SUPPORTS |
| `nli` | bidirectional NLI only (contradiction ≥ 0.5 → CONTRADICTS, entailment ≥ 0.5 → SUPPORTS) |
| `llm_direct_claims` | one LLM call returns the label from the two claim sentences |
| `llm_direct_context` | the same, with the passages and abstracts the pair analyser sees |
| `rules_full` | ClaimGraph without an LLM: lexicon context, surface stance, rule decision |
| `rules_no_gate`, `rules_no_stance` | its ablations |
| `hybrid_full` | **ClaimGraph**: NLI + LLM stance + grounded LLM context table → the same rule decision |
| `hybrid_no_gate` | − context gate: every conflict signal is CONTRADICTS |
| `hybrid_no_stance` | − stance: NLI alone raises conflicts; the context gate still applies |
| `hybrid_no_nli` | − NLI: stance and context only |
| `hybrid_no_grounding` | − quote check: the LLM's context table is trusted unverified |
| `hybrid_always_qualify` | degenerate gate: every face-value conflict becomes QUALIFIES |
| `hybrid_always_abstain` | degenerate gate: the system abstains on every face-value conflict |
| `always_qualifies`, `always_unrelated` | constant classifiers |
| `v2_*` | the V2 comparability model in place of the gate (not adopted) |

Each system is a pure function of a pair record, so adding a system or changing a threshold needs no new LLM calls.

## Labels

**Two levels.** A *relation* (SUPPORTS, EXTENDS, QUALIFIES, CONTRADICTS, or UNRELATED) and, for pairs that conflict at
face value, a *conflict verdict* (genuine, context-dependent, insufficient). A conflict a system sees but does not assert
(CONTRADICTS flagged uncertain, verdict insufficient) is scored as an abstention. `results.md` also reports the reading
in which it counts as the CONTRADICTS relation it is filed under.

**Four-state protocol (batches `c4` and `f1`).** Per pair: face-value stance, evidence sufficiency, context
comparability, final status (NONE / GENUINE / CONTEXT_DEPENDENT / INSUFFICIENT_EVIDENCE) and explanatory factors. The
reference is the per-dimension majority of three annotator models and is **not adjudicated**.

**Five-way protocol (batch `eval2`).** Blinded model-assisted consensus labels with researcher adjudication; they are not
human or expert annotations. Three annotator models label every pair; unanimous labels are taken, every other pair is
flagged for the researcher, who also re-checks a random sample of unanimous ones. `gold.json` keeps each model's label
and justification, the consensus, the flag, the adjudicated label and where the final label came from.

In both protocols the annotator models come from three providers (`google/gemini-3-flash-preview`,
`qwen/qwen3.7-plus`, `anthropic/claude-haiku-4.5`), none of them the pipeline's model. They label zero-shot from the
claims, passages, titles and abstracts only; no system output reaches them (`backend/tests/test_annotation_models.py`).
Annotation calls never touch the pipeline's LLM cache.

## What is frozen

`FREEZE.json` records when the decision rules, prompts, baselines and metrics were fixed, with the SHA-256 of the files
involved, and lists the later changes it records, with their reasons. `annotation/f1/PREREGISTRATION.md` fixes the design and the
success criteria of the fresh-topic validation, which was run once; its result is in `results/f1_validation/`. Files whose
latest recorded hash still matched, and `fresh_validation.py`, whose hash the validation records, are published
unmodified. For `experiment.py`, `annotation.py`, `scoring.py`, `model_annotation.py` and `topics.json` the shipped file
differs from the last hash recorded for it (see "Verifying the freeze"); they are published as they stood when the
project was finalised.

## Verifying the freeze

```bash
python eval/verify_freeze.py        # from the repository root; needs only the standard library
```

The script reads `FREEZE.json` and never writes anything. It checks, against the files in this repository, the last hash
recorded for every path, the hashes written into the text of the addenda (the pre-registration, the fresh-topic result
files, the scoring code) and the `scorer_sha256` stored with the fresh-topic results. It prints `OK`, `DIFF` or `MISSING`
for each and exits 1 if any is not `OK`. It does not update hashes.

On this repository it reports 19 `OK` and 5 `DIFF`, and exits 1. The five are known and are not hidden: `FREEZE.json`
was not rewritten. CI does not run this script; it exits 1 on the shipped tree because of these five known differences.
A missing file would be reported as `MISSING`, separately from a `DIFF`.

| File | Last hash in `FREEZE.json` | Shipped file | File's last-modified time in the development repository (IST) |
|---|---|---|---|
| `backend/app/evaluation/annotation.py` | addendum 2026-10-06T15:02 | differs | 2026-10-06 15:55, after the record |
| `backend/app/evaluation/experiment.py` | addendum 2026-10-06T16:40 | differs | 2026-10-06 19:35, after the record |
| `backend/app/evaluation/scoring.py` | addendum 2026-10-06T16:40 | differs | 2026-10-06 19:40, after the record |
| `backend/app/evaluation/model_annotation.py` | addendum 2026-10-06T16:40 | differs | 2026-10-06 16:17, **before** the record |
| `eval/topics.json` | initial freeze, 2026-10-06T14:51 | differs; the file also holds the three `fresh` topics (2 dev, 6 test, 3 fresh in total), which the 2026-10-07T01:10 addendum describes | 2026-10-07 00:59, after the record |

How far these can be explained:

- `annotation.py`, `experiment.py` and `scoring.py`: the modification time is later than the record, consistent with
  edits after the hash was taken. `FREEZE.json` does not record those later versions, so the repository cannot say what
  changed.
- `model_annotation.py`: the file was last modified before the addendum that records its hash, so a later edit is not
  shown. Either the recorded hash was taken from a different version, or the file was rewritten without its timestamp
  changing. The repository cannot tell which.
- `topics.json`: removing the three `fresh` topics does not reproduce the recorded hash, so they are not shown to be the
  only difference.

Modification times are weak evidence (copies and editors can reset them) and are given only as a pointer. All five
differences predate the preparation of this repository: the shipped files are byte-identical to the development
repository's. Every other recorded hash matches, including the pre-registration, `fresh_validation.py` and the
fresh-topic result files.

## Metrics

Defined in `backend/app/evaluation/metrics.py`: false contradictions per 100 pairs, false-contradiction rate,
contradiction precision / recall / F1, per-class precision / recall / F1, macro-F1 over the five relations, accuracy,
verdict accuracy on reference face-value conflicts and confusion matrices, each with a 95% bootstrap interval (items
resampled within sampling strata). Ablations, baselines and degenerate gates are compared to the full system with a
paired bootstrap on the same items. The studies on batches `c4` and `f1` resample paper pairs and score out of fold,
leaving one topic out.
